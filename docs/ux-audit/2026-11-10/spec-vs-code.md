# SPEC редизайна против кода (только чтение, 2026-11-10)

Пути от ~/dev/raoden-loom. SPEC = docs/ux-audit/2026-11-10/redesign/SPEC.md.

## 0. Главное

1. В таблице 37 «причин», в коде 32 причины паузы. Пять лишних (push_protected, push_not_confirmed, push_option_field, mcp_present, mcp_unchecked) причинами паузы не являются. Остальные 32 совпадают по ключам 1:1.
2. Заголовки, кнопки и тексты причин в коде уже есть: `orchPause_<причина>_what/_why/_do/_button` (i18n.ts ~1989–2105, ru). SPEC называет свои тексты «черновик по смыслу ключей, сверить с кодом». Сверять надо с orchPause_*, а не с orchReason_*.
3. Для 11 причин смысл кнопок у дизайнера не совпадает с тем, что main реально принимает (раздел 1.3).
4. Вкладка «Действия» (activity) в коде это лента событий по ролям, а не «действия». SPEC отправил её не туда (раздел 2).
5. Тем «Бумага/Иней» нет, «следовать системе» и «меньше прозрачности» тоже. Выбор палитры и фона холста хранятся двумя независимыми полями, правило «sage→Песок+Камень+Пастель» надо делать миграцией (раздел 3).
6. Запрет повторной пары связей в main есть (`link_duplicate`). Поля `bend` нет нигде, нужны тип, метод стора, IPC и preload (раздел 4).

- В таблице SPEC лишние 5:

- Команды main (OrchestrationRunCommand, shared/orchestration.ts:165–189): pause_after_turn, stop, resume, step, answer, clarify, recover (accept / retry_turn / reset_to_checkpoint), raise_limit, dismiss, checks.decide (accept/edit), finish.confirm, check.amend, person.decide, plan.decide, permission. ### 1.3 Расхождения по строкам (смысл/действие). Формат: что у дизайнера → что в коде → правка

1. provider_limit_at / provider_limit. Главная «Продолжить в {at}» → автопродолжения в назначенное время нет (нет команды-таймера). Реально: `resume` сразу; кнопка в коде «Продолжить», текст `orchNext_provider_limit_at` (i18n.ts:1077–1078): «дождитесь сброса или смените аккаунт, затем Продолжить». Правка: главная «Продолжить», время сброса показывать подписью; вторичное «Оставить на паузе» убрать (оно и так на паузе), вторичная реальная «Остановить запуск». В autopilot есть своё ожидание лимита (taskBoard.ts AutopilotLimit), но это доска, не панель.
2. limit_reached. «Поднять до {next}» и «Завершить запуск» → raise_limit: пользователь вписывает значение строго больше текущего, виды turns/roundsPerStage/replans/runMs (orchestrationService.ts:2677–2686; кнопка «Поднять лимит и продолжить», i18n 2024). После raise main ставит user_request-паузу, дальше resume. Правка: поле значения в зоне действия (дизайнер уже так нарисовал, Н7), «Завершить запуск» заменить на «Остановить запуск» (stop даёт статус stopped, не completed).
3. awaiting_checks_decision. **Неверно целиком.** SPEC: «Проверки не прошли: n из m», «Вернуть исполнителю», «Принять без проверок». Код: лид ПРЕДЛОЖИЛ команды проверки, до решения работа стоит. Команда `checks.decide`: «Принять» как есть или «Изменить» (до 16 строк, без дублей) (orchestrationService.ts:2692–2701). Заголовок «Лид предложил команды проверки»; вариант «не нашёл команд» = `awaiting_checks_none` (можно вписать свои или продолжить без проверок) (i18n 2081–2088). Правка: главная «Решить по командам» (принять), вторичная «Изменить»; в варианте none главная «Продолжить без проверок»/«Вписать команды». «Проверки не прошли» это совсем другая вещь: её в журнале нет как паузы (провал проверки уходит в раунд исправления лидом).
4. awaiting_finish_confirmation. SPEC: «Всё готово — подтвердите завершение» / «Завершить запуск». Код: запуск завершён БЕЗ проверок, push и QA только после явного согласия по каждому шагу; команда `finish.confirm` с tree/commit и решением confirm/decline отдельно для push и QA (shared/orchestration.ts:178; i18n 775, 2089–2092). Правка: заголовок «Нужно согласие на отправку и выкладку»; два переключателя «Отправить push / Выложить на QA» (подтвердить или пропустить) и одна главная «Решить про отправку».
5. check_needs_permissions. SPEC: «Разрешить для этого запуска» / «Пропустить проверку». Код: ОДНА команда `check.amend` (orchestrationService.ts:2712+): человек сохраняет строку проверки (изменённую или нет) как СВОЮ команду, она идёт без песочницы. «Запустить команду лида без песочницы» намеренно запрещено владельцем (комментарий там же: «There is no run the lead's command without the sandbox»). «Пропустить» нет. Правка: главная «Изменить команду» (поле с командой, кнопка «Сохранить как свою»), вторичная «Остановить запуск».
6. plan_review. «Один этап и стоп · Изменить» → кнопка «Начать работу по плану» (resume, i18n 2000); есть `step` («Один шаг», не «этап»), есть «Уточнить» (clarify, текстом, не правкой плана), «Остановить». Правка: «Один этап» → «Один шаг»; «Изменить» → «Уточнить задачу». Планы также принимают `permission` (ExitPlanMode Claude): запрос плана приходит как permission.kind="plan" (RunPanel.tsx:576–582), его в SPEC нет.
7. awaiting_answer. Вторичная «Пусть решит сам» → такой команды нет: answer требует непустой текст ≤ 8000 (orchestrationService.ts:2658–2664). Правка: убрать; оставить «Ответить» и «Остановить запуск».
8. outcome_unknown. SPEC: главная «Проверить изменения и продолжить», вторичные «Повторить ход», «Остановить». Код: `recover` с тремя действиями: accept («Принять результат хода», главная, i18n 2012), retry_turn («Повторить ход»), reset_to_checkpoint (вернуться к контрольной точке, нужен confirm; в режиме «в папке проекта» запрещено: «never written into the project», orchestrationService.ts:2677 область). Правка: добавить третье действие «Вернуться к контрольной точке» (контурное danger с подтверждением, скрыть в режиме project).
9. invalid_report / protocol_error. «Попросить отчёт заново» → `step`, кнопка «Повторить ход»; resume ЗАПРЕЩЁН (STEP_ONLY). Правка: главная «Повторить ход»; «Открыть отчёт/ответ» = вкладка «Ход работы», «Подробно». Для protocol_error совет «обновите Claude Code/Codex» (i18n 2019). Тон: в PAUSES ждут человека (Ж), SPEC даёт «О»: допустимо визуально, но свечения тогда не будет, а по коду «Waiting for you». Согласовать.
10. permission_denied. «Вернуть ход агенту», «Разрешить и повторить» → код: resume после того, как человек обновил Claude Code или поменял права в настройках проекта (i18n 2025–2028). Заголовок «Исполнитель не может начать работу» (режим или версия CLI), а не «Действие отклонено: {action}» (отклонённых действий в этой причине нет: отклонение разрешения это команда permission во время хода). Правка: перенести заголовок, кнопка «Продолжить», вторичная «Настройки проекта».
11. lead_modified_tree. **Неверно.** «Откатить изменения лида» → такой команды нет; причина STOP_ONLY: только stop. Решение «оставить эти правки» человек принимает во вкладке «Изменения» и потом ставит цель заново (i18n 2033–2036). Правка: главная «Остановить запуск», вторичная «Посмотреть изменения»; «⚠ Оставить и продолжить» убрать (resume отклоняется).
12. shared_git_tampered, journal_corrupt, sandbox_unavailable. «Проверить и восстановить», «Восстановить из контрольной точки», «Проверить снова», «Как включить», «Скопировать журнал» → у всех трёх (и lead_modified_tree) единственная команда stop; текст «Остановите запуск и задайте цель заново» (i18n 2041–2052). sandbox_unavailable: совет «впишите свои команды проверки без песочницы». Не-macOS: набор `sandbox_unsupported` («Здесь нет песочницы», i18n 2053). Правка: главная везде «Остановить запуск»; «Скопировать журнал», «Скопировать id» это допустимые локальные кнопки без команды.
13. loop_suspected. «Продолжить с подсказкой / как есть / Остановить» → реально: «Уточнить» (clarify, текстовое поле, было в Обзоре внизу), потом resume («Дать ещё раунд»), stop. Правка: поле «Уточнить» должно жить в зоне действия (в SPEC поля нет, см. п. 2: clarify потерян).

Правка: главная «Решить» открывает список пунктов, у каждого свой сегмент; «одной главной» кнопки на пункт нет.

Правка: главная «Вернуть лиду» (безопасная), вторичная «Принять» с выбором по пунктам.

Код: действие ПОСЛЕ успеха (commit/push/QA) выполнено, но результат не подтверждён (i18n 1472, 2069–2072). Две кнопки: «Проверить результат» (resume: только проверка, повторно не выполняет) или «Повторить» (если шаг упал, `finishPending(view).status==='failed'`, runModel.ts:409). Правка: заголовок «Не подтверждено, что коммит, отправка или выкладка прошли»; главная «Проверить результат» / «Повторить».

Код: модель взята из ~/.codex/config.toml, человек меняет её в Codex (`/model`) и нажимает «Продолжить» (i18n 1076). «Настройки проекта» (RoleModels) могут задать модель роли, но для текущего запуска не действуют. ## 2. Вкладки 8 → 3 (RunPanel.tsx:1560, useAgentCanvasUi.ts:12)

Ключ вкладки → заголовок (i18n 1088–1092, 1679, 1849): plan «План», result «Результат», summary «Итог», overview «Обзор», activity «Действия», changes «Изменения», log «Лог», history «История». Для newer вкладки без changes (RunPanel.tsx:1560).

Что потеряно или неверно в таблице SPEC:
1. **«Действия» (activity) неверно понята.** SPEC: «Зона действия над вкладками + меню …». Код: `activity` = живая лента событий по ролям (сообщения, мысли, вызовы инструментов, файлы) с переключателем Лид/Исполнитель/Проверки и индикатором молчания (`silenceFor`) (RunPanel.tsx:1753–1760, 1888–1892; FEED_KINDS 294). Кнопки управления это отдельный блок над вкладками. В трёх вкладках нужно место для ленты: «Ход работы» с режимом «Лента» (не «Подробно»).
2. Переключатель ролей (lead/executor/check) есть у activity и log (RunPanel.tsx:1753). В SPEC роли не упомянуты. Нужен общий фильтр в «Ходе работы».
3. «Обзор» (overview, RunPanel.tsx:1783–1887) содержит: факты результата (factLines, finish-шаги commit/push/QA с хэшами, `observed` версия QA), «Где изменения» (ветка/папка), участники (протокол, доступ, модель роли, фаза, «Наблюдать»), SessionEnvironment, Differences, время и лимиты (elapsed/turns/stage/roundsPerStage), список этапов плана, список проверок, **поле «Уточнить» (команда `clarify`)** и ReviewExport. SPEC обещает «Параметры, дубли удалены» и не называет: участников/модели/доступ, лимиты/время, окружение сессии, **поле «Уточнить»**, ReviewExport (экспорт ревью board-review/v1, F4). SPEC оставляет «Итог и Ход работы» и скрывает «Изменения»: «Ход работы» должен включать ленту и лог, иначе содержимое потеряно. «Неизвестно этой версии» для неизвестных полей: в коде есть `compatible` и `fallback {line,code}` (shared/orchestration.ts:310–312): fallback означает «только цель и записи», это надо показать как отдельное состояние. Команды при newer блокируются через `view.newer` (runStatus.ts:120), плюс есть действие «отпустить связь» `releaseNewer` (canvasStore.ts:240+, UI `ReleaseNewerLink`, AgentScene.tsx:14); в SPEC его нет, а без него связь с запуском новой версии не освободить.
9. Заголовок панели (summary-блок над вкладками, RunPanel.tsx:1588+): он компактный на всех вкладках кроме overview, это и есть «зона действия». ## 4. Изгиб связи bend {along, across}

Где живёт связь:
- Тип: `OrchestrationAgentLink {linkId, fromAgentId, toAgentId, createdAt, runIds[]}` и `OrchestrationCanvas {agents, links, owners?, releasedNewerRuns?}` (src/shared/orchestration.ts:549–564). Интерфейс API: `createLink`, `deleteLink` (618–619). Метода обновления связи нет.
- Хранение: файл канвы `{v:1, ...}` через `canvasStore.save` (src/main/services/orchestration/canvasStore.ts:~125–150). Чтение `load()` отдаёт `links` как есть без разбора по полям (строка 121–128), запись сериализует объект целиком, а `read()`/`withRuns` копирует связь спредом (`{...l, runIds}`, строка 164). То есть лишнее поле `bend` на диске и при чтении НЕ потеряется, если будет записано; формат `v:1` менять не обязательно (старый файл без bend читается).
- Нужно добавить:
  1. `bend?: { along: number; across: number } | null` в `OrchestrationAgentLink` (shared/orchestration.ts).
  2. Метод стора `setLinkBend(linkId, bend)` через `change(...)` с проверкой: link найдена (`linkOf`), `Number.isFinite` по обоим, диапазон (иначе файл разрастётся мусором), `null` = сброс. Правка не должна требовать `busy`: изгиб не меняет запуск.
  3. Канал IPC: `IPC.orchestrationLinkSetBend` (contracts.ts IPC-таблица), обработчик в src/main/ipc/orchestrationIpc.ts рядом со 355–356 (`uuid(linkId)`, числа), `manager.setLinkBend` (manager.ts ~1816), preload src/preload/orchestrationClient.ts:57–58, метод в `OrchestrationApi` (shared/orchestration.ts:618).
  4. Рендер: сейчас связь это прямая `Line from={rightMid(from)} to={leftMid(to)}` (AgentScene.tsx:115–125). Кривая Безье, ручка, стрелка это новая отрисовка; `chipCenter/chipSize` (linkChip.ts) и `linkTrace.ts` рассчитаны на прямую, чип «у середины со смещением» придётся пересчитать.
  5. Тесты на сохранение: файл, повреждение (`.damaged-<uuid>`, 134), и что `createLink` с тем же `linkId` возвращает существующую связь (идемпотентно, 219–223): `bend` оттуда не должен затираться.
- Нюанс: у карточки «одна связь» в UI (`linkOf(card)` берёт первую, AgentScene.tsx:86–87), а запусков на связь несколько (C1, до 4 живых, AgentScene.tsx:69–80). Чип связи один на связь, выбор запуска (`picked`) в SPEC не отражён.

Запрет повторной пары:
- ДА, есть: `if (c.links.some(l => l.fromAgentId === from.agentId && l.toAgentId === to.agentId)) refuse("link_duplicate", "these cards are already linked")` (canvasStore.ts:~228). Идемпотентность по `linkId` (219–223) отдаёт существующую связь, а не ошибку.
